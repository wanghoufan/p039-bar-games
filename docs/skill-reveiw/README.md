## 候选 1｜派工切碎法（builder 大单必超时）

- **触发场景**：给 builder 派一单要改多个文件、或跨多个模块的活。
- **问题现象**：本项目历史上大单必超时留半成品（B1 大单超时**零落盘**、D1 超时、D1 返工两次）。
- **沉淀动作**：每单只给 **1~2 个文件 + 1 条明确验收命令**；派工单必须写清「不许 commit/push」「不许碰哪些文件」「改完贴真实命令输出」。本轮 30 单零超时零半成品。
- **验收标准**：单文件 + 单门禁能在一次实调内收敛。
- **备注**：与 override 表的 builder 超时策略配套（超时先查落盘再续派，不盲重派）。

## 候选 2｜QA / Reviewer 派工防呆句（"别等 supervisor"）

- **触发场景**：派 QA 或 reviewer 角色。
- **问题现象**：本轮 QA-2 **实测全部做完**，却因误以为「要先等 supervisor 确认才能落盘」而空转一轮、报告未写。
- **沉淀动作**：QA 派工单模板**固定加一句**：「**实测完成立即把报告写入 `docs/qa/` 并给出总判定，落盘不需要等 supervisor 或任何人确认**（主链顺序是 Builder → Reviewer → QA → Supervisor，supervisor 在你之后）。」
- **验收标准**：QA 汇报里不再出现「等待确认」字样。

## 候选 3｜fail-closed 计数与出卡/门槛解耦的耦合检查

- **触发场景**：任何「A 条件不满足就不计数」的 fail-closed 规则，而 A 又同时是另一个系统（出卡池、档位、进度）的**唯一驱动源**。
- **问题现象**：本轮产品级 P0 —— 披露信号恒 undefined ⇒ 有效信息轮恒 0 ⇒ Heat 恒 H1 ⇒ H1 桶仅 8~10 张 ⇒ **任何单玩法局第 9 轮必然 PACK_EXHAUSTED**，且互选窗口永不可达。
- **沉淀动作（检查四问）**：
  1. 这条 fail-closed 计数**同时**驱动了哪些下游（出卡池过滤 / 档位 / 进度 / 互选门槛）？
  2. 若它恒为 0，下游会出现「空池」还是「有池但取不到」？
  3. 解除耦合时，豁免必须**下沉到判定内部**（`bucket()`），**不能只换取卡来源不同步计数**——否则 `assessExhaustion` 仍会判耗尽（半改无效）。
  4. 豁免判据要用**逐卡派生**（如「是否 Formal 卡」），不要用**id 前缀字符串**。
- **验收标准**：解耦后计数/证据/互选**全部保持冻结**，只放开「取哪张卡」。

## 候选 4｜新 Formal 内容入库纪律（AI 审查语境）

- **触发场景**：把新题/新内容纳入正式库（如 Formal Fixed Manifest）。
- **问题现象**：机器 BAR-FIT 全 PASS 掩盖了 4 张人工不合格（价值审视腔、AI 腔、套话风险、封闭式二选一信息增量单薄）。
- **沉淀动作（七条）**：
  1. **机器档位不得当人工结论**（`machineVerdict` ≠ `humanBarFit`）。
  2. **审查者身份必须如实标注**（本轮由 AI 角色审查，`source` 写明「product-reviewer(Research Reviewer, AI 角色)」，不得冒充真人）。
  3. **宁少勿滥、不凑数**（Human 明确：不要预设张数；没信息增量的就别写）。
  4. 缺口**靠补内容，不靠放宽门槛**（阈值/样本/超时/±18% 一律不动）。
  5. 迭代方式：**审查 → 按意见重写 → 复审**，直到达标；复审要**独立读真实文本**，不能只信转述。
  6. 报缺口必须给**可执行补卡建议**（哪个玩法、多少张、什么 `heatMax`/`intensity`/topic 覆盖），并声明**结论不可外推**。
  7. 旧内容**零修改**（既有题面不动，新内容用新 ID）。
- **验收标准**：逐卡四条件准入可复算；空审查输入重建 ⇒ 正式库为 0（证明 reviewed 只来自审查输入）。

## 候选 5｜「生产 Heat 恒 H1」下的新卡 `heatMin` 律

- **触发场景**：任何新增内容卡要进入受 Heat 硬过滤的正式轨，而**生产侧 Heat 推进链尚未打通**（如披露信号未落地）。
- **问题现象**：`heatMin≥2` 的新卡在生产永远抽不到；若把既有卡改判 Formal，等于**删库存**，会重演已修好的断粮 P0。
- **沉淀动作**：新卡 **`heatMin` 一律 1**；用 `heatMax` 拉开以备将来 Heat 推进；入库前跑 Router MC 验证「生产实况 Heat 档下该卡是否可被抽到」。
- **验收标准**：MC 报告出现 `pack_exhausted=0` 或等价证据。

## 候选 8｜事实与账本互斥的自查（通道切换如实记录）

- **触发场景**：叙述里要写「本轮换了模型/通道」之类事实。

## 候选 9｜测试断言「按输入派生」而非硬编码数量

- **触发场景**：产物数量会随人工判定/内容迭代变化的测试（如 `formal fixed = N`）。
- **问题现象**：三轮人审导致测试连红三次（`formal` 0 → 20 → 23 → 24），每次都要改测试。

- **验收标准**：再次人审改动不需要改测试；且 fail-closed 断言（空输入 ⇒ 正式库 0；非 PASS 不入）逐条保留或加强。

## 候选 10｜提交前卫生清单（含 next-env.d.ts）

- **触发场景**：任何 commit 之前。
- **问题现象**：`next-env.d.ts` 每次跑全量 E2E 都被 Next 自动改回 `.next/dev/types` 变体，混进提交就是噪声。

- **验收标准**：暂存区无禁入文件；推送后工作树 clean。

## 候选 11｜临时探针必须还原 + sha256 自证

- **触发场景**：为定位问题临时改代码/插桩/篡改数据。
- **问题现象**：本项目历史上有 agent 谎报产物（「已写入某文件」而磁盘上没有）。
- **沉淀动作**：探针用完**立刻还原**，并给 `shasum -a 256 <file>` 前后比对 + `git status` 对比；结论要贴**真实命令输出**，失败如实报「未修好」。
- **验收标准**：报告里能看出「篡改实现 → 相关用例应变红」的判别力证据。

## 候选 12｜mac 剪切板交付的避坑流程（用户反复强调）

- **触发场景**：把长文本（提示词/汇报）交给用户转发。
- **问题现象**：剪贴板可能被覆盖/冲突，用户需要可重新复制的源文件。
- **沉淀动作**：`cat file | pbcopy` → **立即** `pbpaste | wc -c` 回读字节数 → `pbpaste | head -c N` 看开头 → `diff <(pbpaste) file` 判 `IDENTICAL`；**验证失败就不报告「已复制」，直接重试**；长文本优先分段或走已验证通道；同时**必须**在项目 `temp/` 落一份完整 MD 并给绝对路径。
- **验收标准**：字节数一致 + 首尾正常 + `diff` 一致，三者同时成立。

## 候选 13｜过期数字「标注作废」而非删除或并列

- **触发场景**：MC/统计口径变化后，旧报告里的数字失效。
- **问题现象**：旧 MC 数字（`heatAtDraw` 25/25/24.5/25.5、dead-end 41.5%）与新数字并存会误导。
- **沉淀动作**：在**原处**加显式「已作废 + 新真源路径 + 作废范围」标注，**保留原数字**（历史留痕），**不重写、不并列**；机械生成的报告只加指针、不手工改内容。
- **验收标准**：任何报告都能一眼看出自己是否 stale。

## 候选 14｜连续执行的「允许停机」判定（不停机也不越权）

- **触发场景**：用户要求「一口气连续做完，不要问是否继续」。
- **问题现象**：既要不停机，又不能在未授权情况下改 Human 冻结规则。
- **沉淀动作**：只有五类情况允许停——①必须改变 Human 已冻结产品规则；②高风险不可逆操作；③必须决定尚未冻结的最终产品规则（如 final Mutual 的 HEAT/TIMING）；④必须新增未批准 UI；⑤真实外部阻塞（权限/登录/验证码）。**其余（含低风险可逆问题、测试失败、builder/QA 汇报）一律自行判断并继续**；遇到局部阻塞时，**其他不受影响的工作继续做**。
- **验收标准**：整轮只有 0~1 次找人，且那次确实是上面五类之一。

## 第二批（本轮新增，2026-09-29；承接第一批 14 个候选）

### 候选 15｜产品方向变更时，先固化「内容基线」再动内容
- **触发**：Human 说「主线不再是 X，而是 Y」这类**方向级**变更。
- **做法**：先把新基线写成可执行条目（场景约束 / 退出清单 / 重点清单 / 优先级序 / 字段 / 机器规则 / Reviewer 维度 / 统计目标），落进 `docs/handoff/HANDOFF.md`，**再**派 Reviewer 逐卡重审。旧口径（例：上一版「保留 18 / 改写 13」）**必须显式作废**，不能沿用。
- **验收**：审计结论的分类从「保留/改写/删除」换成新口径（如 KEEP/REWRITE/REPLACE），且**方向级不适配的卡要能被判 REPLACE（换新 ID）而不是只改字**。

### 候选 16｜Reviewer 判「方向不适配」时走新 ID，不要硬改
- **触发**：一张卡的核心信息目标已经变了。
- **做法**：新建 ID（旧卡退出 Formal），理由是 provenance / payloadHash / review 历史 / MC trace / 调试都更清楚；只有「同核心问题、仅题面缩短口语化」才保留 ID。**同一 ID 不表示完全不同的语义。**
- **验收**：新 ID 有全库 collision test；被替换的旧 ID 确实退出 review admission。

### 候选 17｜被判 REWRITE/REPLACE 的内容要**立即退出 Formal**
- **触发**：已入库内容被新基线判为不合格。
- **做法**：先把旧版本置 `UNREVIEWED` 并移出 Formal，通过审查后才回。**「一边承认不合格、一边继续当正式内容」是自欺。** 接受 Formal 数下降。
- **验收**：`build:fixed-manifest` 里被换掉的卡不在 `formalFixed.allowedCardIds`；`formal` 数字下降有据可查。

### 候选 18｜机器规则跟不上新基线时，先升级机器再谈通过率
- **触发**：机器预筛把明显不合格的内容判 PASS。
- **做法**：把新基线的**高风险词/结构**落成机器规则（如「五年后/长期关系/上一段关系/各占几成/哪三段/最近一次……当时怎么决定」⇒ 至少 SUSPECT 强制 Reviewer 看），**不机械全 HARD_FAIL**；**禁止**为提高通过率调阈值。
- **验收**：新规则能复现地命中历史漏判样本；篡改判定的测试会红。

### 候选 19｜「偏好信息 ≠ 接触授权」必须写进内容纪律
- **触发**：内容里出现身体/亲密偏好字段（哪怕只是 planning-only）。
- **做法**：显式写死两条：① 任何身体互动任务仍必须**可跳过**、不因之前回答自动授权、不做强迫动作；② planning-only 字段（如 `followUpHook`）**先不改 Runtime Schema**，证明有用后再单独设计接入。
- **验收**：代码/文档里搜不到「回答即授权」的语义；字段标注为 planning-only。

### 候选 20｜Golden Sample 当内部风格基准，不当停机关卡
- **触发**：多次出现「内容跑偏」类返工。
- **做法**：选出少量（≈12）风格标杆题作为**内部**基准，后续每轮 Reviewer 必答「这张和基准放一起像不像同一个产品」；**不为它停下来问 Human**。
- **验收**：每轮审查记录里有这句对照结论；偏严肃/抽象/长期/咨询/AI 的题即使信息量高也不 PASS。

### 候选 21｜同一次会话里用户可能切换任务，交接件要能被新指令覆盖
- **触发**：用户在大交接流程中途又给了新提示词。
- **做法**：把已完成部分照常收口（clean 提交 + 记录），把**未完成的交接件**（HANDOFF 段、skill 沉淀、commit、接续提示词）并入新任务的第一步；**不要因为新指令把已 push 的工作留在未提交脏树里**。
- **验收**：新任务开始时工作树跟踪文件 clean；新指令的基线写进 HANDOFF 而不是散在聊天里。

### 候选 22｜预存脏改动先单独提交隔离，再开新战场
- **触发**：开工时工作树已有一批**与本轮无关**的改动（治理同步、他人并发工作等）。
- **做法**：先核对这些改动与本轮目标无关 → **单独一个 docs 提交**收口（附「未提交/未触碰」的清单与理由）→ 再开本轮；**禁止**恢复/覆盖/删除/stash 未知来源改动，也禁止把它们混进本轮内容提交。
- **验收**：本轮 commit 的文件清单里没有预存改动；预存改动要么被单独收口、要么保持原样且有记录。

### 候选 23｜「预存脏文件」若本轮必须追加，只追加不覆盖
- **触发**：本轮需要改的文件已经在脏状态（例如规则文件、经验文件）。
- **做法**：先读 diff → 保留已有改动 → 只追加本轮内容 → 提交时按 hunk 粒度确认没吞掉别人的行。
- **验收**：提交后 `git diff` 里原有改动仍在；本轮新增行可单独指出。

## 第三批（酒吧主线内容重构 A2~A9，2026-09-29；承接前两批 23 个候选）

### 候选 24｜「退出正式轨」不等于「不会被抽到」——退役内容必须移出运行时内容源
- **触发**：把一批已入库内容判为不合格、移出正式轨（Formal/正式清单）。
- **问题现象（本轮 P0 级）**：26 张退役卡（前任深聊/心理咨询/人生规划）退出 Formal 后**仍留在运行时内容源**；因「legacy 不受 Heat 硬过滤」的既有豁免，它们**照样被抽到、照样计有效轮**——**直接违反新内容基线**，等于一边说不合格一边继续漏给玩家。
- **做法**：退役 = ①退出 Formal ＋ ②**移出运行时内容源**进归档文件（带 `retiredAt`/`retireReason`/原字段全留）＋ ③加断言「归档文件不被任何运行时路径 import」＋ ④加断言「退役 ID 不出现在任何运行时卡池」。历史审查证据一律不删。
- **验收**：`build:fixed-manifest` 的 `legacy` 计数下降且可解释；退役 ID 只存在于归档文件与历史审查 JSON。
- **通用化**：任何「正式轨 / 兼容轨 / 灰度轨」并存的内容系统，退役时都要问一句：**兼容轨的豁免规则会不会让它继续被消费？**

### 候选 25｜统计口径禁止「主字段 OR 辅助字段」重叠计数
- **触发**：给内容/覆盖率/占比设指标，而对象上有多个可归类的字段。
- **问题现象**：builder 报的覆盖率来自「`category` **或** `hook`」的重叠计数函数，把卡面真值 `attraction 2 / follow_up_hook 1` 报成 `attraction 4 / follow_up_hook 19`，**指标虚假达标并因此放行**。
- **做法**：①**只按主字段真值**统计，辅助字段**单列**；②测试里**断言「真值 ≠ 重叠口径」**，让两种算法永远同时可见；③禁止用「主字段或辅助字段」满足阈值；④报告里必须同时给出两个口径（或明确写「重叠口径仅对照、不用于放行」）。
- **验收**：有人改统计函数成重叠口径时测试变红；报告里能一眼看出真值。

### 候选 26｜「不同轴/不重复」类断言不能只比字符串或标签
- **触发**：要求「同档不同轴」「不重复」「钩子可兑现」这类**语义级**约束，却想用机检兜底。
- **问题现象**：用「动作帧字符串不同」当达成证据，放过了 `274 vs 275`（字符串「组队 vs 狼人杀」不同，但答案必然同一人）和 `270 vs 278`（轴名不同但同轴）。
- **做法**：①字符串/标签机检**只能当审计辅助**，不得当达成证据；②要落**语义级签名**（同档内不得共享同一「提问对象 + 答案空间」）；③判据文件里**自述是必要条件还是充分条件**（本轮自述「必要条件非充分证明，抓不住纯换词改写」）；④**禁止为了让现有数据全过而把判据写成空壳**；⑤确实无法改开的重复，**上报裁决**，不许改判据迁就内容。
- **验收**：判据给出对现有数据的真实判定数字（判重对数 + 误杀数），不是「全过」。

### 候选 27｜派工单的指标与定义冲突时：定义优先，指标是我写错的就认账改指标
- **触发**：我给 builder 的派工单里，「必须 1:1 保留旧方向」与「必须覆盖 H1~H4 且 `flirt≥2`」同时出现，而旧卡天然不可能满足后者。
- **问题现象**：builder 只能二选一——要么违反定义（换向），要么违反指标（凑数），然后把冲突顶回来。
- **做法**：①**产品定义（V1.3 里的定义）优先于我临时加的指标**；②裁决时明确说「这条指标是我写错的」，不要含糊成「builder 执行有偏差」；③把指标**下移到能承担它的批次**；④派工单里**不要同时出现定义与派生指标**而不做可行性交叉检查。
- **验收**：返工派工里不再出现「同方向重写 + 覆盖 H3/H4」这类互斥要求。

### 候选 28｜半成品红门禁的收尾：先如实提交并标注，再补断言；不许回滚换绿
- **触发**：一轮开发在「改锁定断言」这步被打断（限频/超时/会话结束），代码已生效但门禁红。
- **做法**：①**先核对实际落盘状态**（`formal` 实际值、产物文件），分清「半成品」与「真回归」；②**提交时如实写明半成品与失败数**，红门禁不许掩盖；③HANDOFF 写清**断点位置与恢复第一步**；④⛔ **不许回滚已生效的业务改动去换绿测试**，也不许注释断言/改阈值；⑤**不许改测试去迁就半成品**——测试的旧值本来就该更新。
- **验收**：接手者读完 HANDOFF 就能直接续上，不用重新诊断。

### 候选 29｜E2E 换端口必须三处同改（`baseURL` / `webServer.url` / `webServer.command --port` / spec 内硬编码 URL）
- **触发**：默认端口被**别的项目**占用（本项目 3000 被 `019-ing` 的 `vercel dev` 长期占着），要换端口跑 E2E。
- **问题现象（本轮踩坑）**：只把 `baseURL` 改成 3017 → `webServer` 命令仍去抢 3000 → **60s 超时，测试根本没跑**；改对端口后仍剩 6 条失败，因为两个 spec 里**硬编码** `127.0.0.1:3000`。
- **做法**：换端口必须**同时**改 ①`use.baseURL` ②`webServer.url` ③`webServer.command` 加 `--port` ④spec 里硬编码的 URL；跑完 `git checkout --` 还原受保护文件并核对 `git diff` 为空。
- **验收**：E2E **0 failed** 才算通过；**不接受「N 条端口伪失败」**这种说法。治本项（把 spec URL 改为从 `baseURL` 派生）列为待办。

### 候选 30｜工具报 429/超时 ≠ 没执行：必须核对实际落盘，再判定是否重派
- **触发**：外部 CLI 通道（codebuddy/codex）调用返回 429、限频或超时。
- **问题现象（本轮）**：A9 的两次调用都秒回 429「限频至 2026-09-30 15:46」，看起来完全没执行；但实际 `formal` 已变成 57（**当时值**；现役已经 R6/R7 降至 `53`，见 HANDOFF「大交接 4」）、审查 JSON 已写入 219 处记录 —— **工作做完了，只是最后几次模型调用撞上限频，报告没吐出来**。若照字面「重派」，会重复劳动甚至互相覆盖。
- **做法**：①遇 429/超时**先核对落盘**：`git status` 改动集、关键产物值、测试实跑结果；②只有**确认零落盘**才重派；③**落盘了但门禁红**＝半成品，按候选 28 收尾；④报告纪律：**reported 与 actual 不一致时以 actual 为准并如实说明**。
- **验收**：恢复开发的人看到的是「A9 断在改测试断言」，而不是「A9 没跑，重跑一遍」。

### 候选 31｜planning-only 字段与 Runtime 字段的统计必须分开
- **触发**：为便于设计/审查新增了一批**只用于规划与审查**的字段（`category`/`followUpHook`/`expectedAnswerShape`），本轮明确不改 Runtime Schema。
- **做法**：①统计与覆盖率**只用主字段真值**，planning-only 字段单列；②**必须加断言锁死「这三个字段未进入 Runtime / GameCard 正式 schema」**（在 `schemas.ts`/`v2-types.ts`/metadata/bridge 里 0 命中）；③报告中显式标注「planning-only，本轮未接入运行时」；④将来要接入运行时**必须单独设计并走 Plan 变更**，不得顺手改。
- **验收**：搜正式 schema 0 命中；测试里有对应锁。
